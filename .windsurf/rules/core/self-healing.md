# Self-Healing Synthesis

**Activation:** Glob — pause-state, circuit-breaker, abuse-prevention, watchdog, health endpoints, the per-project `docs/RESILIENCE.md` (deployed scaffold types emit it; client-app and static types do not), and the service spec.
**Purpose:** **Self-healing in Fabrik = an autonomous-by-default escalation LADDER, NOT a new primitive.** Every step on the ladder is implemented by a primitive that already exists in [`58-resilience`](58-resilience.md), [`60-watchdog`](60-watchdog.md), [`75-workers-jobs`](75-workers-jobs.md), or a vendored fabrik-lib module. This pack's job is to **order** those primitives into one strict response chain per failure class so a service degrades gracefully instead of failing loud and panicking.

**Distinction from adjacent packs:**

- [`58-resilience`](58-resilience.md) — defines preventive primitives (timeout, retry, circuit-breaker, pause-state). Each primitive bounds one failure mode.
- [`60-watchdog`](60-watchdog.md) — the escalation engine and the owner of its tiers. Tier A acts automatically (it registers `restart_container`, `clear_file_cache`, `scale_concurrency`, `pause_worker`); Tier B is opt-in; Tier C escalates — and carries the **approved-write lane** (`drop_queue_items`, `rotate_locks`), off by default; **Tier D** (opt-in, Telegram-gated) applies a tested code fix with auto-rollback. ⚠️ Registered is not runnable — see **What the sidecar can execute today** below.
- **This pack** — the *order* in which those layers run per failure class.

## The escalation ladder

Each row reads left-to-right: **Symptom** (an observable signal) → **First response** (a `58-resilience` primitive or the module that implements it) → **Fallback** (another primitive or a `60-watchdog` action) → **Escalate** (operator-bound). The agent picks the row matching the active failure, walks left-to-right, and **stops at the first step that resolves**. Never skip rightward.

| # | Failure class | Symptom (observed) | 1. First response | 2. Fallback | 3. Escalate |
| --- | --- | --- | --- | --- | --- |
| 1 | **OOM** (main container memory exhaustion) | `RestartCount` delta, with `State.OOMKilled: true` / exit 137 in `docker inspect`; host metrics show mem% > 95 % for >2 m (the sidecar samples no memory). The kernel's oom-killer line lands in the HOST kernel log, not the container's `docker logs` stream — the watchdog's `oom_kill` log regex can only match a line the app itself writes, so its restart-count pass is what fires | Docker `restart: unless-stopped` restarts the killed container itself, with growing back-off between attempts (compose contract, [30-ops](30-ops.md)) | Watchdog Tier A `restart_container` (idempotent; refuses shared-infra targets per [60-watchdog](60-watchdog.md)) | Watchdog Tier C → Apprise; the deadman restarts the container once, `watchdog.deadman_timeout_seconds` later |
| 2 | **Queue backlog** (workers can't keep up) | `queue_depth` gauge climbs; `oldest_unfinished_age_seconds` > worker SLA | Adaptive worker pool scale-up ([75-workers-jobs § Adaptive Worker Pool](75-workers-jobs.md)) | Raise the pool ceiling `WORKER_MAX` ([75-workers-jobs § Adaptive Worker Pool](75-workers-jobs.md)) — an operator or deploy change. The watchdog's `scale_concurrency` cannot do it: it writes `/opt/<id>/.env` and runs `docker compose` inside a sidecar that mounts the project read-only at `/project`. Dropping the oldest items (`drop_queue_items`) is the Tier C **approved-write** lane — needs `WATCHDOG_ALLOW_DB_WRITES=true` and a writable `WATCHDOG_DB_URL_RW`, and is unreachable today (below) | Watchdog Tier C → operator; consider raising `WORKER_MAX` |
| 3 | **Upstream rate-limit** (vendor 429 / quota exceeded) | `_429` counter spike; `Retry-After` header present (delay-seconds or an HTTP-date) | Honour `Retry-After` inline, CLAMPED, per [58-resilience § Basic Resilience](58-resilience.md); when the refusal is class-wide, `pause_state.set_global_pause(resource, reason, ttl_sec=min(retry_after, cap))` — the vendor value is clamped before it becomes a queue-wide TTL | `async-http-client`'s `CircuitBreakerRegistry` flips OPEN for that upstream until a probe succeeds | Watchdog Tier C → operator; check vendor billing |
| 4 | **Upstream timeout / network blip** | repeated `httpx.TimeoutException` or `httpx.ConnectError` from one upstream | `pause_state.maybe_pause_from_error(msg)` — classifies via `classify_transient_error(msg) → (resource, ttl_sec) \| None` and sets the pause flag. Its built-in patterns match DNS, connection-refused and SSL-EOF messages, NOT httpx timeouts (`ReadTimeout('timed out')` classifies as `None`): register a timeout pattern first with `register_error_pattern(keywords, resource, ttl)`, or call `set_global_pause` directly on `httpx.TimeoutException` | Circuit breaker OPEN; queued work waits on the pause flag, not on the dep | Watchdog Tier C when the pause outlives `4 × ttl_sec` (dep is wedged, not transient) — measured by the first-set timestamp the project stores itself ([58-resilience § Banned Patterns](58-resilience.md)); `set_global_pause` is a sliding SETEX and the sidecar counts nothing |
| 5 | **Signup flood** (abuse: bot signups + disposable emails) | `signups_per_ip_per_minute` ratio > threshold; disposable-domain hit rate high | `abuse-prevention` rejects at the registration route — `check_disposable_email(email)` and `check_ip_rate_limit(…)` before any DB write — with progressive quota unlock (`grant_immediate_quota` / `schedule_delayed_grant`) for legitimate users | Watchdog Tier A `pause_worker` for the `signup` resource (Redis SETEX `<prefix>:pause:signup`, where `<prefix>` is the project id (not a spec field — the spec rejects `project_prefix`) — the app's `PAUSE_KEY_PREFIX` must be `<project_id>:pause:`: the fabrik-lib module defaults to `app:pause:`, the scaffold template to `{SERVICE_NAME}:pause:`) — unreachable today (below) | Watchdog Tier C → operator; consider IP-range UFW block on the hub |
| 6 | **DB connection-pool exhaustion** | `pool.get_size() == pool.get_max_size()` for >30 s; new requests time out in `await pool.acquire(timeout=…)` | App-side: `await pool.close()` then reopen, behind a `POST /admin/reset-db-pool` endpoint the app implements itself on port 8000 (no scaffold emits it) that checks `X-Internal-Token` against `SERVICE_INTERNAL_SECRET_KEY` | Watchdog **Tier B** `reset_db_pool` (opt-in via `watchdog.auto_tier_b`; `X-Internal-Token` guarded) | Watchdog Tier C → operator; check for connection leak in code, not pool size |
| 7 | **5xx burst** — a downstream API failing, or this service's own responses | Downstream: the breaker's trip threshold (`async-http-client` default: 3 consecutive 5xx within 60 s). Own responses: the app's own 5xx counter. The watchdog's `http_5xx_spike` trigger (5 or more 5xx status lines in the last 200 lines / 120 s of `docker logs`) matches only plain-text access lines; a scaffolded service logs its access lines as JSON, where the status code ends a quoted string, so the trigger stays blind there | Circuit breaker OPEN against that endpoint; serve cached fallback if present (graceful degradation per [58-resilience § Banned Patterns](58-resilience.md) "No fallback on external call failure") | Watchdog Tier A `pause_worker` for the impacted resource if it gates a worker queue — unreachable today (below) | Watchdog Tier C → operator; the deadman restarts and re-alerts once, `watchdog.deadman_timeout_seconds` later |
| 8 | **Stuck jobs / row locks** (a claimed row not released) | On the scaffold queue schema: `status='processing'` with `updated_at` past the visibility timeout; on a queue that carries an explicit lock column: that column (default `locked_at`) past `now() − interval` | Worker's own orphan-sweep task ([75-workers-jobs § Orphan Sweep](75-workers-jobs.md)) — on the scaffold schema this is the whole remedy | Watchdog Tier C **approved-write** `rotate_locks` (bounded by `max_age_sec` ∈ [30, 86400]; applies only to a queue with an explicit lock column) — needs `WATCHDOG_ALLOW_DB_WRITES=true` and a writable `WATCHDOG_DB_URL_RW`, and is unreachable today (below) | Watchdog Tier C → operator; investigate why workers crash mid-lock |
| 9 | **Code-level regression / new critical exception** | new unhandled-exception spike (error-tracker critical) or 5xx tied to a recent deploy | Watchdog **Tier A** stabilize — `restart_container` only; rolling back a deploy belongs to Tier D | Watchdog **Tier D** tested code-fix, Telegram-gated (approve / timeout-apply), auto-rollback on regression ([60-watchdog § Tier-D code-remediation gate](60-watchdog.md)) — opt-in only | Watchdog **Tier C** → operator if the fix can't be made green |
| 10 | **Provider death / silent stall** (an unattended loop makes ZERO forward progress while running) | the loop's exported progress counter is flat past its threshold — **watch PROGRESS, not error codes**: a guard that watches one status code is blind to every other failure shape | Rebuild the chain from live survivors (direct-provider path), or rely on the gateway mechanism the project DECLARED (see [58-resilience § Provider-death resilience](58-resilience.md)) | The last-resort rung — which is only a rung if it has actually been **exercised**; an untested fallback is a silently-dead one | ONE operator alert, cleared on recovery — exactly-once and clear-on-recovery are the project's to build ([58-resilience § Provider-death resilience](58-resilience.md)); `alerting/` only suppresses a repeat of the same title within `ALERT_MIN_INTERVAL` |

**⚠️ Row 10 is NOT the deadman timer, and the difference is the whole point.** The Tier-C deadman below
(`spec.watchdog.deadman_timeout_seconds`, 60–3600, default 300 s, rendered as `WATCHDOG_DEADMAN_TIMEOUT`) measures **operator silence** — it arms only
*after* an escalation (a Tier C alert, a Tier A/B action that skipped, was refused or failed, or a budget cap), fires ONCE per incident, and its action is `docker restart`. The sidecar has no acknowledge path today (filed upstream), so resolving the incident does not stop that restart. Row 10
fires when **no alert was ever raised**, because zero progress is not an error: it is the *absence* of
events, and nothing else in this corpus watches for an absence.

**Why a strict order matters:** skipping rightward (e.g., escalating Tier C before letting the circuit breaker try) trains the operator to ignore alerts; falling-back leftward (e.g., re-trying the upstream while the breaker is OPEN) defeats the breaker. The ladder enforces both.

## Integration with watchdog

The right-hand columns map to [`60-watchdog`](60-watchdog.md) tiers; 60-watchdog owns their switches and defaults. The spec's `watchdog:` block is what `fabrik apply` turns into the sidecar's environment. Concretely:

- **What the sidecar can execute today:** it dispatches every diagnosed action with an EMPTY parameter set (the diagnosis schema carries no parameters — filed upstream), so an action that needs a parameter is refused at validation. Only `restart_container` (Tier A) and `reset_db_pool` (Tier B, port defaulting to 8000, and only with `auto_tier_b`) can run. `pause_worker`, `scale_concurrency`, `clear_file_cache`, `wipe_redis_cache`, `install_log_drop_rule`, `create_fix_pr`, `drop_queue_items` and `rotate_locks` are registered but unreachable — this ladder names four of them: in rows 2, 5, 7 and 8 the watchdog step resolves to Tier C escalate plus the deadman restart. Treat each row's first response as the step that actually heals.
- **Tier A (autonomous, default):** row 1 uses `restart_container`, row 9 stabilizes with it; rows 5 and 7 name `pause_worker` (unreachable today). No operator approval, no opt-in flag.
- **Tier B (opt-in via `spec.watchdog.auto_tier_b: true`, rendered as `WATCHDOG_AUTO_TIER_B`):** row 6 uses `reset_db_pool` — it POSTs `/admin/reset-db-pool` on the main container's port 8000 with `X-Internal-Token: $SERVICE_INTERNAL_SECRET_KEY`. Defaults to "skipped → escalate Tier C" until the spec author flips it on.
- **Tier C approved-write (opt-in per project; unreachable today):** rows 2 and 8 name `drop_queue_items` and `rotate_locks` — app-DB mutations, so they could run only when the project's `.env` sets `WATCHDOG_ALLOW_DB_WRITES=true` AND a writable `WATCHDOG_DB_URL_RW` exists (`fabrik apply` provisions the DML-only role; nothing sets the switch for you). Off, they skip and the row escalates.
- **Tier C (escalate-only):** any row where the fallback step fails → Apprise → Telegram. The deadman then runs `docker restart <main_container>` once, `watchdog.deadman_timeout_seconds` (default 300 s) after the escalation, and re-alerts with `[DEADMAN-TIMEOUT]` — whatever the operator does, since nothing acknowledges it today.
- **Tier D (opt-in via `spec.watchdog: { auto_code_fix: true, propose_fix_prs: true, trigger_sources: [error_webhook], critical_paths: [<error-type or URL-path substrings>] }` — the spec validator refuses the first without the second; the code-fix path runs only on trigger-bus signals, and of the schema's sources (`emitter`, `health`, `error_webhook`) the sidecar registers only `error_webhook` today; with GlitchTip's default webhook every alert arrives as an `exception`, which pages, and so reaches Tier D, only when it matches `critical_paths`):** row 9 applies a code fix — generate + test, Telegram-gate (Approve / Reject / STOP, or silence-window auto-apply), deploy, **auto-rollback on a health regression**, STOP kill-switch. The driver refuses Tier D without a git source and degrades it for an app with no HEALTHCHECK (a blind rollback); the sidecar refuses to start it without `WATCHDOG_TELEGRAM_BOT_TOKEN` and `WATCHDOG_TELEGRAM_CHAT_ID` (or the unprefixed `TELEGRAM_*` pair) in the project `.env`; while Tier D is on, every page-worthy signal is first stabilized with `restart_container`, whatever its failure class; `WATCHDOG_TEST_CMD` overrides the default test command `pytest -q`. Off by default → row 9 falls back to Tier A stabilize + Tier C escalate. The approval window's value and its knob are 60-watchdog's — see [60-watchdog § Tier-D code-remediation gate](60-watchdog.md).

If a failure class doesn't appear in the table above, the rule is: **add the row to this pack first, then the response logic to the code.** Never silently invent a self-healing response — it'll diverge from the operator's mental model and break the ladder's discipline.

## Anti-patterns

These look like self-healing but aren't:

1. **Retry-without-backoff loop.** A `while True: try: call(); break; except: continue` against a wedged upstream is a denial-of-service against your own downstream. Use `tenacity` with **jittered** backoff (`wait_random_exponential` or `wait_exponential_jitter` — bare `wait_exponential` is banned per [58-resilience § Basic Resilience](58-resilience.md)), or `pause_state.set_global_pause(resource, reason, ttl_sec)` if the failure is class-wide.
2. **Catch-all `except: pass` on upstream calls.** Silent swallow is data loss; you've removed the only signal a watchdog could see. Pattern from [58-resilience § Banned Patterns](58-resilience.md): classify → pause → re-raise.
3. **Kill-and-restart-everything panic.** When something goes wrong, restarting `traefik` + `postgres-main` + `redis-main` + all tenant containers (any panicked operator script) breaks every other tenant. The watchdog's `_FORBIDDEN_TARGETS` set (`/opt/fabrik-lib/watchdog/watchdog_sidecar/actions.py`) blocks 14 shared-infra names; honor the same list in any operator script. (The sidecar's own deadman restart does not re-check that list — filed upstream.)
4. **Self-healing without a visible signal.** A pause flag, breaker, or rate-limit reject that doesn't increment a counter and emit a structured log line is invisible — when it misfires, you can't tell. Every ladder step MUST emit a counter AND a `structlog.info()` (or `pino.info()`) row carrying the resource name + reason; without that, the next operator audit has no way to tell the difference between "step fired and recovered" and "step never ran". **Tier-D steps (stabilize / remediate / apply / rollback) are held to the same bar:** each MUST emit a counter + structured log AND write the `incidents` / `approvals` / `deploys` tables — an unaudited or irreversible code-remediation is not self-healing, it's an unreviewed deploy.
5. **Operational-failure-as-content-verdict.** Recording a timeout / network error as a terminal "this item is bad" decision means the next retry will re-fetch and re-fail; the pause-state pattern's whole point is that operational failures are transient ([58-resilience § Operational failures are transient](58-resilience.md)). Default transient/retryable; require positive content evidence before flipping terminal.

## Worked example — SaaS skeleton under signup flood

A SaaS (`shape.kind=service`) using the standard skeleton wires three primitives into one coherent ladder for the signup-flood failure class:

1. **First defense — `abuse-prevention/`** vendored into `libs/abuse_prevention/`. The registration route calls `check_disposable_email(email)` and `check_ip_rate_limit(…)` BEFORE any DB write; disposable-email domains and per-IP rate caps reject in-process. Legitimate users go through the progressive quota unlock (`grant_immediate_quota`, then `schedule_delayed_grant`).
2. **Fallback — `pause-state` (Redis-backed).** When `signups_per_ip_per_minute` for a specific IP stays high after the first defense's per-IP cap fires, the worker emits an incident; the watchdog sidecar reads the inbox and proposes Tier A `pause_worker` with `resource=signup_<ip_hash>` (the action accepts `^[a-z][a-z0-9_]{0,31}$` and a TTL of 5–3600 s, so truncate the hash to fit — and it is unreachable today, above, so until upstream carries parameters the app sets this pause itself with `pause_state.set_global_pause(...)`). Every signup-handling worker checks `pause_state.is_paused("signup_<ip_hash>")` from the vendored fabrik-lib `pause-state` (the scaffold's own `pause_state.py` has no `is_paused`), with `PAUSE_KEY_PREFIX` equal to `<project_id>:pause:`, and bails without touching the DB. Never gate other workers on `is_globally_paused()` while per-IP keys share the prefix — it reports ANY key under it, so one IP would stop them all.
3. **Escalate — Watchdog Tier C → Apprise → Telegram.** If the pause keeps being re-set — the app counts re-stamps against the first-set timestamp it stores, since the sidecar counts nothing — the abuse is sustained, not transient, and the app raises the incident that sends the watchdog to Tier C with the IP hash + symptom counters. The operator decides whether to add a UFW deny rule on the hub — the watchdog does NOT touch UFW.

**What's notably missing from this ladder:** `iptables -A INPUT -s <ip> -j DROP` as a Tier A action. Network-level mutation against arbitrary IPs is operator-only because mis-classifying a carrier-grade-NAT address would ban every subscriber sharing it; the breaker stays at the application layer.

## Acceptance checklist (when shipping a per-project ladder)

- [ ] `docs/RESILIENCE.md` exists per [58-resilience § Per-Project Contract](58-resilience.md). Every external dep has a row.
- [ ] Each ladder step in the per-project doc names a primitive that exists in `fabrik-lib/` or a numbered rule pack — no inventions.
- [ ] Each step emits a Prometheus counter + a structlog row carrying the resource name (no silent action).
- [ ] If a row references Watchdog Tier B (currently row 6), the spec carries `watchdog: { auto_tier_b: true }`, the app implements `POST /admin/reset-db-pool` on port 8000, checking `X-Internal-Token` against `SERVICE_INTERNAL_SECRET_KEY` (the action calls it; nothing emits it), and the operator has been notified of the opt-in.
- [ ] The per-project ladder does not count on a watchdog step that is unreachable today (`pause_worker`, `scale_concurrency`, `drop_queue_items`, `rotate_locks`): each such row's healing step is the app's own first response, and the doc says the watchdog step escalates. If the approved-write lane is wanted once it is reachable, the project `.env` sets `WATCHDOG_ALLOW_DB_WRITES=true` and the RW DSN is provisioned.
- [ ] If a row references Watchdog Tier D (currently row 9), the spec carries `watchdog: { auto_code_fix: true, propose_fix_prs: true, trigger_sources: [error_webhook], critical_paths: [...] }`, the app has a HEALTHCHECK, the project `.env` carries the Telegram bot token and chat id (and `WATCHDOG_TEST_CMD` if the tests are not `pytest -q`), and `code_fix_window_sec` is set deliberately rather than left to a default — its knob is in [60-watchdog § Tier-D code-remediation gate](60-watchdog.md); the Telegram Approve/Reject/STOP loop is wired; every apply/rollback writes the `deploys` table; auto-rollback on health regression is armed. Absent the opt-in, row 9 stays Tier A stabilize + Tier C escalate.
- [ ] No anti-pattern from the section above is present in code: ruff `S110`/`E722`/`BLE001` pass (the gate), and every hit of `grep -rnE "except[^:]*:[[:space:]]*(pass)?[[:space:]]*$" src/` — an inspection list that also shows re-raising handlers — is read and none swallows an upstream failure, and every `while True:` loop that `grep -rn "while True:" src/` finds carries a backoff and an exit.
- [ ] The worked-example pattern (3 layers, last layer is always operator-bound) is the shape of every per-project ladder. If your ladder has >3 fully-autonomous layers, you've crossed into "panic" territory — collapse the bottom two into one explicit step and document the operator-bound terminal. **A Tier-D code-remediation step counts as operator-bound, NOT a fully-autonomous layer** — the Telegram approval (or the configured silence window) IS the operator-bound terminal — *provided* the gate is enabled, every apply is auditable (`deploys` table) and reversible (auto-rollback + STOP). Without that gate it reads as a 4th autonomous layer and this checklist rejects it.
