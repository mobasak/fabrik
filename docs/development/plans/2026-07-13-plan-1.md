## D1 — `_deploy_git` never validates the compose file (fail-open on the standard path)

**What's wrong.** `_validate_compose()` enforces the Fabrik compose invariants: `container_name`, `deploy.resources.limits.memory`, `platform: linux/amd64`, no host `ports:`, and no stray legacy `coolify` network. It has exactly **two** call sites:

- `deployer_ssh.py:373` — inside `_deploy_template` (`def` at `:333`)
- `deployer_ssh.py:481` — inside `_deploy_docker` (`def` at `:455`)

`_deploy_git` (`def` at `:404`, body runs to `:454`) clones/pulls and goes straight to `docker compose build && up -d --wait` — **it never calls `_validate_compose` at all**.

**Why it matters.** Git-sourced is the *standard* Fabrik project deploy path (per `CLAUDE.md`: "the VPS runs `git pull` from the GitHub remote"). So in normal operation the invariants are **advisory, not enforced**. A git-sourced compose with no memory limit, a host `ports:` binding, and an Alpine base deploys cleanly — and the missing memory limit is exactly the OOM footgun the invariant exists to prevent on the shared VPS.

Secondary: even where `_validate_compose` *does* run, it never checks per-service **network membership**. It only rejects a stray `coolify` key and a declared `fabrik` network that isn't `external: true` (`:737-741`). A compose declaring **no** `networks:` block passes — the code's own comment says so ("not all composes declare networks at top level").

**Proof (executed 2026-07-13):**
```
_deploy_git calls _validate_compose : False    (template + docker paths: 2 call sites)
_validate_compose(<compose with no networks block>) -> []      # passes
```

**Fix direction.** Call `_validate_compose(compose_content)` in `_deploy_git` after the clone/pull, before `docker compose up`. Decide deliberately whether a missing `networks:` block should fail — today it silently passes.

## D2 — An uncapped watchdog is reachable; the cost-cap validator is dead on the apply path

**What's wrong.** There are two different watchdog config paths, and they disagree:

- **`fabrik apply`** parses the spec with `yaml.safe_load` (`orchestrator/validator.py:200`), returns a plain **dict** from `load_and_validate` (`:331-343`), and the orchestrator assigns that raw dict straight to `ctx.spec` (`orchestrator/__init__.py:136-137`). The Pydantic `WatchdogConfig` model is **never constructed**. (`validator.py` mentions `spec_loader` exactly once — in a *comment* at `:318`. It imports no pydantic.)
- The **`WatchdogConfig` model** (`spec_loader.py:361`) carries `enabled: bool = False` (`:379-380`), `daily_budget_usd: float = 1.0` (`:389-390`), and a `model_validator` that rejects both-caps-zero (`:621`).

So on the apply path:
1. The sidecar is **opt-OUT**, not opt-in — `infrastructure.py:268` reads `watchdog_cfg.get("enabled", True)`. A spec with **no** `watchdog:` block gets a sidecar.
2. The real cap defaults come from the **driver's** raw-dict reads: `drivers/watchdog.py:526-527` → `$5.00/day` + `200 invocations/day`. The model's `$1.00` default never applies here.
3. The both-caps-zero validator **never runs**, so a spec with `daily_budget_usd: 0` + `daily_invocations_cap: 0` **deploys a genuinely uncapped sidecar** — an LLM-calling loop with no cost ceiling.

And the validator can't even catch it when it *does* run: it short-circuits on `if self.enabled and …`, and `enabled` defaults to `False` — so zeroed caps without an explicit `enabled: true` are accepted by the model too.

**Proof (executed 2026-07-13):**
```
validator uses yaml.safe_load: True ; imports pydantic: False
resolve_applicability({... "watchdog": {"daily_budget_usd": 0, "daily_invocations_cap": 0}})["watchdog"]
  -> (True, 'spec.watchdog.enabled=true')          # deploys, uncapped
WatchdogConfig(daily_budget_usd=0, daily_invocations_cap=0)
  -> ACCEPTED (enabled=False)                      # validator short-circuits on `enabled`
```

**Fix direction.** Pick one: either have `apply` validate the `watchdog:` block through `WatchdogConfig` (so the cap validator actually runs), or move the cap check into the raw-dict path in `infrastructure.py`/`drivers/watchdog.py`. Also reconcile the two default sets — the model says `$1.00`, the driver says `$5.00`; one of them is lying to whoever reads it. Separately, decide whether the validator should fire on zeroed caps regardless of `enabled`.

## D3 — `audit-registrars` has no watchdog audit function

**What's wrong.** `_REGISTRAR_ORDER` (`infrastructure.py:90-101`) has **10** registrars, including `watchdog`. But `audit.py:521-531` `_AUDIT_FUNCS` has only **9** entries — `watchdog` is absent. `audit_all` falls through to `AuditResult(status="unknown", detail="no audit function registered")`.

**Why it matters.** `audit-registrars` is the tool an operator uses to ask "is this project's infra actually provisioned?" For the watchdog it can only ever answer **`unknown`** — so a sidecar that failed to deploy, or one that deployed when it shouldn't have, is invisible to the audit.

**Proof (executed 2026-07-13):**
```
_AUDIT_FUNCS = ['authelia','backrest','gatus','glitchtip','grafana','meilisearch','postgres','prometheus','redis']
'watchdog' in _AUDIT_FUNCS : False        # 9 audit fns for 10 registrars
```

**Fix direction.** Add a `watchdog` entry to `_AUDIT_FUNCS` that checks the sidecar container exists on the target VPS and reports its configured caps.

## D4 — `destroy --use-state` leaks the watchdog governance directory

**What's wrong.** There are two teardown paths:

- `destroy_deployment` calls `_destroy_watchdog_governance` (`destroyer.py:349`) **unconditionally** at `:598` — its docstring even says cleanup "must not depend on the current spec still declaring a watchdog." Correct.
- `destroy_from_state` (`destroyer.py:756-771`, reached via `cli.py --use-state`) calls `_destroy_app`, `_destroy_dns` and `_destroy_files` — and **never** `_destroy_watchdog_governance`.

**Why it matters.** `/var/lib/watchdog-governance/<id>` survives a `--use-state` teardown, accumulating stale governance dirs on the VPS. This is the more likely path in practice: `--use-state` is what you reach for when the spec is already gone.

**Proof (executed 2026-07-13):**
```
destroy_from_state removes governance dir : False
_destroy_watchdog_governance call sites   : only :598 (the spec-driven destroy path)
```

**Fix direction.** Call `_destroy_watchdog_governance` in `destroy_from_state` too. It is already documented as idempotent, so this is safe.

## Behavior Contract

One test per defect — each must FAIL against today's code (that is what proves the defect is real) and pass after the fix.

- **Given** a git-sourced spec whose `compose.yaml` omits `deploy.resources.limits.memory`, **When** `_deploy_git` runs, **Then** it raises/aborts with the same validation error `_deploy_template` produces today. (Currently: deploys cleanly.)
- **Given** a compose with **no** top-level `networks:` block, **When** `_validate_compose` runs, **Then** the intended outcome is asserted explicitly — pass or fail, but decided, not incidental. (Currently: passes silently.)
- **Given** a spec with `watchdog: {daily_budget_usd: 0, daily_invocations_cap: 0}`, **When** `fabrik apply` resolves it, **Then** it is rejected as an uncapped LLM cost path. (Currently: `resolve_applicability` returns `(True, 'spec.watchdog.enabled=true')` and it deploys.)
- **Given** a spec with **no** `watchdog:` block, **When** the driver renders the sidecar env, **Then** the caps it writes match the caps `WatchdogConfig` documents. (Currently: driver `$5.00`/200 vs model `$1.00`/200 — they disagree.)
- **Given** a project whose watchdog sidecar is deployed, **When** `audit-registrars` runs, **Then** the watchdog row reports `present`/`missing`, not `unknown`. (Currently: always `unknown` — no audit fn.)
- **Given** a deployed project, **When** `destroy --use-state` runs, **Then** `/var/lib/watchdog-governance/<id>` is gone. (Currently: it survives.)
- **Mocked:** the SSH/Docker transport is mocked (no real VPS); `resolve_applicability`, `WatchdogConfig`, `_validate_compose` and the `_AUDIT_FUNCS`/`destroy_from_state` call graphs are exercised for real.
