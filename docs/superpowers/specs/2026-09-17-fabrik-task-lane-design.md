## Goal

Add one command, `/fabrik-task`, that carries a small change with one reversible decision from "I have a change" to "committed, pushed, reviewed, recorded" in one run record, keeping every gate and decision the spec chain makes and dropping only its intermediate artifacts and their separate reviews — and give every agent a decision rule it can apply **before drafting** to choose between three lanes.

## Why this exists

**The cost, measured from `~/.claude/state/command-feedback.jsonl` on 2026-09-17** (re-derive before citing; the ledger is live):

| lane | runs | median per run | total |
|---|---|---|---|
| `fabrik-spec` · `fabrik-spec-review` · `fabrik-plan-after-chat` · `fabrik-plan-review` | 65 | 85 min | 158 h |
| `fabrik-execute-plan` | 30 | 259 min | 210 h |
| `fabrik-review-scoped` + `fabrik-command-improve` (the light lane) | 79 | 31 min | 50 h |

A full chain is ~6 hours before a line is written, ~10 with execution. The light lane is 32 minutes. **There is nothing between them.** So an agent holding a change with one real decision either pays the chain or skips design.

**Both failure directions, executed in one session (2026-09-17):** the same one-paragraph edit to `commands/_sources/fabrik-review-scoped.md` was attempted three times as an elaborated mechanism — 3 review rounds, 35 findings, 22 confirmed, confirmed/own-fix 10/0 → 6/6 → 6/6 firing the D-278 stop, the third cut regressing the rendered corpus — and all three reverted; then once correctly sized: 130 B, converged on pass 2 with 0 confirmed defects, findings 8→3 with zero confirmed (commit 02df9b74f, D-288; the round series is the review's own close row, feedback ledger ts `1789671544.7596035`, `rounds 2 (0→0)`). The difference was not care; it was WHEN the sizing test was applied. The contract's existing test (CLAUDE.md § Behavior, the mail SIZING step, D-097) is sound and was applied to the *draft* — which, once elaborated, genuinely was a mechanism.

**The asymmetry that decides the default:** over-sizing costs ~6 hours before any code; under-sizing costs one ~30-minute review, with the review as the backstop. Those are not symmetric risks. The lane exists to make the cheap direction the default without making it the *unreviewed* direction.

## Chosen approach

**One command, one run record, the D-row as the durable artifact. It SEQUENCES existing mechanisms and RESTATES none.** The command's source is glue between four things that already exist as fragments or contract text — the run record, the FIX DIRECTIVE, `/fabrik-review-scoped`, the close-out feedback — and it adds exactly two new things: the SIZE gate and the DESIGN-in-the-record step.

**Phase 0 — SIZE.** `command_run.py start --command fabrik-task --phases 6 --terminal "<the one-line TERMINAL>" --surface "<the subject, one phrase>" --file <a> --file <b> --file <c> --declare decision=<yes|no>,heavy=<yes|no>,mechanism=<yes|no>,oneway=<yes|no>,tradeoffs=<yes|no>` (every flag the verb already requires is printed, because a line an agent cannot paste is a line nobody runs; `--file` is repeatable and takes ONE path per occurrence, so a path is never split on a separator and a `,` or `:` in a filename needs no rule; a declared path must be a FILE — a directory is refused, because every test below is written over exact paths). **Every test below runs only when `--command` is `fabrik-task`; every other command's `start` BEHAVIOUR is unchanged; `--file` and `--declare` are refused with a one-line message under any other `--command`.** Then:
- **executes** three tests: `files` count ≤ 3; every declared path against the governance-sync regex read from the HUB's `/opt/fabrik/.pre-commit-config.yaml` by absolute path — the file `governance_sync_postcommit.sh:30` opens — never the running repo's copy (executed: `/opt/youtube`'s local `governance-sync` filter differs from the hub's), extracted with a stdlib regex over the YAML text rather than PyYAML, because `command_run.py` is stdlib-only (`:46-60`) and fleet-synced into venvs that mostly lack `yaml`; a hub file that cannot be read fails OPEN with `sync_test: unavailable` persisted beside `declared`, never a refused start on an unreadable or absent hub file (a spoke, a container, a permissions change); and **the moment's one observable** — a declared path that is already DIRTY against `HEAD` at `start` (`git diff --quiet HEAD -- <path>` non-zero, or the path untracked) was worked before the record opened, and the start is refused (`REFUSED — fabrik-task: <file> dirty at start; open the record before the work — or a sibling's WIP on your declared path: message the author`). Executed in a throwaway worktree this run: a clean declared path starts (rc 0), the same path with one appended line refuses (rc 1), an untracked declared path refuses. An mtime comparison cannot express this — every existing file's mtime precedes `started_epoch`, so a test keyed on it either refuses everything or nothing (the first cut of this paragraph was that vacuous test, and its probe proved only that the comparison ran);
- **records** the five declared answers — `decision` (is there one at all? `no` → this is a pure fix, the right-now lane's), `heavy` (§ 1a's heavy surfaces the regex cannot see: any gate/hook/enforcement path outside the sync filter — `.pre-commit-config.yaml` itself, `.githooks/`, `Makefile` — a vendored surface (`libs/subagents/`, the hub clause's current SPEC/PLAN trigger), auth, schema, migrations, concurrency, or work the operator asked for by name — six of the eight classes `/fabrik-review-scoped` itself routes up on, `fabrik-review-scoped.md:15` — the other two are tests 2 and 5 here — so a lane that STARTED on them would open the heavy review nested inside a task record; a crossing found mid-run accepts exactly that nesting deliberately, see UPGRADE), `mechanism`, `oneway`, `tradeoffs` (the decision rule's non-executable tests) — and refuses on `decision=no` or a `yes` to any of the other four;
- **evaluates every test before printing** and on any failure **REFUSES the start**: a LANE test names its lane (`REFUSED — fabrik-task: <test> → <lane>`) with the spec chain taking precedence — `mechanism`, `oneway`, `tradeoffs` or a fourth file name `/fabrik-spec` even when the sync or heavy test also tripped (rule 1's "only if a later test also trips" is this precedence); a sync hit or `heavy=yes` alone names right-now + the full `/fabrik-review` under § 1a as amended by this spec; `decision=no` alone names right-now + `/fabrik-review-scoped`. The three non-lane refusals name the CORRECTION instead: the dirty-at-start message above, `REFUSED — fabrik-task: <p> is outside the repository — declare a repo path`, and `REFUSED — fabrik-task: <p> is a directory — declare files`. Every declared path is normalised to repo-root-relative before any test (`./scripts/x`, `/opt/fabrik/scripts/x` and `scripts/./x` all mean `scripts/x`; a path outside the repo is refused), because the sync regex is `^`-anchored per alternative and a two-character spelling would otherwise clear the lane's most consequential test — executed this run: the three spellings above miss the live filter, the normalised form hits. An ABSENT declared path passes the dirty-at-start check (a new source file is declared before it exists); a PRESENT untracked one refuses. On success it persists `declared: {files, decision, heavy, mechanism, oneway, tradeoffs, sha}` in the record, where `sha` is `git rev-parse HEAD` at start and is what phase 5's committed-overflow branch diffs against. `--surface` keeps its ledger meaning (what the run is OVER — one phrase); the path list lives in `--file`, because `_close` must parse it (U1) and because a unique path list in `--surface` would pollute the column `command_feedback_report.py:941-950` aggregates.
**The moment, honestly.** Command text cannot observe what an agent thought before typing, and the event stream cannot either — it carries 17 event types and no tree-write event, and its per-turn boundary (`stop_pass`, `scripts/sysadmin/kaizen_events.py:109-132`) is too coarse to locate "before drafting" inside a turn. What IS observable is the dirty-at-start check above: work done before `start` is uncommitted on disk when the record opens. Beyond that the moment is a discipline, stated as one, and § The decision rule's tripwire is its named fallback.
This is not a new enforcement check over the tree (D-097's rejected shape); it is the command's own tool refusing an under-specified start, exactly as `done` refuses without `--feedback`. It has a fire rate all the same, and § Validation V0 measures both its base rate and its false-refusal rate before the build.

**Phase 1 — MEASURE.** FIX DIRECTIVE 1 verbatim: reproduce, attribute, name the root cause. `python scripts/select_rules.py --changed <the declared paths>` — the path-scoped form prints the packs whose globs match (`select_rules.py:91-115`; the bare form prints the whole-project ACTIVE/AVAILABLE split, which is not the question) — and those packs are read. The terminal condition is already in the record from `start --terminal`.

**Phase 2 — DESIGN, drafted where it will be minted.** The six fields — PROBLEM · APPROACH · DECISION (reversible?) · MIRROR · OUT · TERMINAL — are written as the D-row's draft text into `<scratchpad>/fabrik-task/<sid>/design.md`, and the record carries only the pointer: `command_run.py step --phase 2 --title "design: <that path>"`. Two facts of `command_run.py` decide this home: `phase_title` is a single scalar overwritten by the next `step` (`:2789`), so fields put there are gone by phase 3; and `pinned_line` interpolates the title verbatim into every response's `RUN:` line (`:254-256`), so fields put there flood every turn. The same six fields are ALSO written once to the record as `design` (a string field `step --phase 2 --design @<scratch>/fabrik-task/<sid>/design.md` sets — a new flag on `step`, whose parser today takes only `--phase`, `--title` and `--review-waived` — and no later step overwrites; `phase_title` cannot be that field because the next `step` replaces it), so the design outlives scratch: a session that dies at phase 3 leaves the fields in the record for the coroner and the resume, not only in a file the janitor sweeps. The draft is read by phase 4's seats from the path and minted as the D-row at phase 5 under a fixed mapping onto the ledger's six-column row, one physical line (`docs/DECISIONS.md:15` — `id | when | who | what | why | where`): `id` from `decisions.py --next-id .` at commit time, `when` the close date, `who` the agent name, APPROACH + DECISION + MIRROR → *what*, PROBLEM → *why* (the ledger's "≤ 2 lines" is a rendered-length bound inside that one physical line), the declared files → *where*; OUT and TERMINAL stay in the record's `design` and are not minted. A literal `|` in any field is written as the entity `&#124;` — a backslash escape does not survive `check_decisions_unique.py:145`, which splits on bare `|` and reports a 7-cell row (executed: the entity reads as 6 cells, `\|` as 7). R4 stands: no new verb. MIRROR is mandatory: the contract's *"every contract change has a MIRROR — name the shape you just broke"*.

**Phase 3 — BUILD.** Plan-lock check first — no CLI exists for it, so the command source carries the read `check_phase_tests.py` does (`.fabrik/plan-locks/` at `:36`, the `*.json` glob at `:46`, `status: active` + `baseline_commit` + `plan` at `:53`, `owned_paths` at `:223`; `check_plan_tickets.py:1051-1053` reads only `baseline_commit` and is not the model): a declared path inside another plan's active lock is a STOP, and so is a declared path that appears in `git diff --name-only <lock.baseline_commit> HEAD` for an active lock that carries NO `owned_paths` — the checker's own fallback (`:245-246`, the files changed since the lock's baseline), inherited rather than guessed narrower; the change and its grader, red-first; shared-append files by the private-index recipe.

**Phase 4 — REVIEW.** `/fabrik-review-scoped` invoked as the skill, unchanged. Its seat briefs carry the phase-2 draft's path and the phase-0 declaration and ask three extra questions — the executed size test re-asked by eye, and the two declarations a reader can refute from the diff: *does the change fit the declared files? did it add a mechanism the declaration said no to (`mechanism=no`)? can you name a second approach the declaration said did not exist (`tradeoffs=no`)?* (`heavy` and `oneway` are not re-asked: a heavy surface shows in the paths and `/fabrik-review-scoped` routes up on it itself, and one-way-ness is the D-row's own classification at mint time). Seats are native (pool OFF, D-181/D-182), as the invoked skill's own banner says. A `yes` to any of the three is the seat's UPGRADE verdict (*this change requires the heavier lane*), which the primary takes — the seats' answers are not row fields: a nested review has no writer onto the parent's row, and the verdict is what the questions exist to produce. Spec-review is thereby folded in: the design is reviewed once, together with what it produced.

**Phase 5 — CLOSE, in this order.** The Doc Sync Matrix rows the change keys (`INDEX.md`, `docs/FEATURES.md`, the dedicated reference doc — the folded `/fabrik-docs-review`; `docs/CAPABILITIES.md` is the corpus's own inventory, not a matrix row), D-row minted from the phase-2 draft (if DECISION was one), CHANGELOG, `docs/LESSONS_LEARNT.md` or `none`, `python scripts/final_gate.py --json` green (Completion Contract 2 — the one GATE the chain keeps, unchanged), commit + push — **then** `done --command fabrik-task --evidence "<proof>" --feedback "<the four fields>"` (the close refuses without either, `:3360-3371`), which re-measures the run's OWN change by the one signal a shared tree offers: the paths whose mtime moved since `started_epoch` (`>= started_epoch - 2`, the slack `command_run.py:3243` uses) over an EXPLICIT candidate set — `git ls-files` plus `git ls-files -o --exclude-standard`, never `git status --porcelain`, which `:3215-3245` walks and which a commit empties: run after the commit, a porcelain-fed re-measure records `0` on every run (executed in a throwaway repo — after `git commit`, porcelain printed nothing while both files' mtimes read moved). The re-measure runs on EVERY close — `done`, `blocked` and `handoff` alike — so the runs most likely to have overflowed produce a size datum; only the `upgrade` field is `handoff`'s alone. Three outcomes, executed in a throwaway worktree this run (declared `a`; `b` edited and committed with `a`; `c` edited and left uncommitted): every moved path in `declared.files` and none matching the sync regex → `oversized_mini: 0`; a path outside the declaration (for an `R` record the destination inherits the source's declared status, so a `git mv` of a declared file is not overflow) that is in `git diff --name-status <declared.sha> HEAD` — committed in this window, which phase 5's order guarantees for the run's own commit — or a DECLARED path that now matches the sync regex; `--name-status` because a RENAME keeps the old mtime and a DELETION has none, so those two shapes are caught on the committed side alone (executed: `git mv` and `git rm` inside the window both show only there) — and, for an `A`/`M` entry, whose mtime also moved → `oversized_mini: 1`, naming the path and the commit from `git log -1 --format=%H <declared.sha>..HEAD -- <path>` (probe: `b` → 1; when that log names no commit — a path introduced only by a merge resolution — the row records `commit: merge`). A `git pull --rebase=merges` taken on § EXIT's push ladder rewrites mtimes and lands paths this run never touched (executed: a merge in the window put an untouched `e.txt` in both signals), and no flag removes them — `--no-merges` changes nothing there, executed — so such a path reads as `1` naming a commit that is not this run's, which its trailer resolves at the operator's read; that is the shared-tree cost, stated, not a defect the machinery hides; a moved path outside the declaration that is still uncommitted → the close cannot tell the run's own overflow from a sibling's write (`:3247-3249`'s comment records that live failure) and it records `oversized_mini: unmeasurable`, naming the path, never a violation attributed to anyone (probe: `c`). If the sync test was `unavailable` at `start`, the close re-runs it; still unreadable → `oversized_mini: unmeasurable (sync_test unavailable)` unless the `1` branch already fired, which wins — the sentinel carries the reason, no third row field (U10) — and a declared path that now matches the regex is the `1` branch's sync arm above, the only state in which it can fire (phase 0 already refuses a declared sync path). Intersecting the measured set with `declared.files` is not a test — a test filtered to its own declaration cannot fail (D-253). Every close writes `oversized_mini` onto the feedback row; a `handoff` whose `--reason` begins `UPGRADE:` (below) also writes `upgrade`. Those are the lane's two row fields; nothing else is added (operator ruling, U10).

**UPGRADE — the one-way ratchet, available from phase 1.** A size input crossing — a fourth file, a verb that must exist, a decision that turns one-way, a trade-off that appeared, or a phase-4 seat's UPGRADE verdict — first MATERIALISES the seed (the phase-2 `design.md` with a `## RESUME` block naming the test crossed; at phase 1, before the design exists, the seed is the `## RESUME` block alone) and then closes `command_run.py handoff --command fabrik-task --resume <that file> --reason "UPGRADE: <test crossed>"`. `handoff`'s `--resume` is `required=True` but nothing validates the path (`:3509`), so the order is the guarantee, not the flag. `/fabrik-spec` opens seeded with that file by the primary's hand — `rec["resume"]` is written, never read back by any script, so the seeding is a stated duty. A `handoff` whose `--reason` begins `UPGRADE:` writes `upgrade: <test>` onto the feedback row (the row carries `state` and not `reason`, so the close parses the prefix and writes the field; a `handoff` for any other sanctioned reason writes none). A SYNC-PATH or HEAVY crossing is keyed to rule 1's lane, not the spec chain, and it does not abandon the change: the run finishes phase 3, runs the full `/fabrik-review` at phase 4 in place of `/fabrik-review-scoped` (seeded with the phase-2 `design.md` as the review brief's design paragraph — that is what the seed carries for a review), discharges phase 5's list in full (matrix rows, D-row, CHANGELOG, `docs/LESSONS_LEARNT.md` or `none`, gate, commit, push), and only then closes `handoff --command fabrik-task --resume <design.md> --reason "UPGRADE: <sync|heavy>" --feedback "<the four fields>"` so the `upgrade` series names which trigger fired — the same fact has one disposition whether it is seen at phase 0 or at phase 3. Nothing downgrades mid-run.

## The decision rule

Applied to the **smallest change that discharges the ask, before drafting** — never to a draft already elaborated:

The blast-radius tests the field publishes come first; the count comes last and is admitted as a house heuristic.

1. touches a governance-sync path — a PUBLIC CONTRACT for ~46 repos? *(executable — the regex)* → **not this lane: right-now + the full `/fabrik-review`** — CLAUDE.md § Completion Contract 1a's heavy-surface list, which this spec's build extends with *"a governance-sync path"* (operator ruling U8) in the hub and template copies and by mail to `fabrik-lib`'s, because at `a929b33f8` (`git log -300`, merges included, files from `git show --name-only --format=`) 52 of the 97 sync-path commits touch only sync paths 1a's current gate/hook/enforcement list does not name — "named" = `scripts/enforcement/`, `.claude/hooks/`, `scripts/final_gate.py`, `.pre-commit-config.yaml` — (`.windsurf/rules/`, `templates/governance/`, `command_run.py`, `docs_updater.py`, `rivals_run.py` …) and would otherwise land one lane lighter. The spec chain only if a later test also trips. Measured: 32% of hub commits trip this test — a third of the hub's work, which IS the synced surfaces; in the 46 project repos, where synced files are never hand-edited, it refuses almost nothing.
1b. a heavy surface the regex cannot see — any gate/hook/enforcement path outside the sync filter, auth, schema, migrations, concurrency, or operator-named work? *(declared as `heavy`)* → **not this lane: right-now + the full `/fabrik-review`** (§ 1a's list as it stands; six of the eight classes `/fabrik-review-scoped` routes up on, `fabrik-review-scoped.md:15` — tests 2 and 5 are the other two).
2. needs a new mechanism — a verb, flag, schema, hook, table, cron — a NEW ARCHITECTURAL COMPONENT? → **spec chain**
3. is the one decision ONE-WAY — structural, public, expensive to unwind? → **spec chain** (the Binding block lives there)
4. are there genuine TRADE-OFFS to adjudicate — a second approach a reviewer could prefer for a stated reason other than taste? *(Google's test; declared as `tradeoffs`)* → **spec chain**. *No decision at all — a pure fix* (declared as `decision=no`) → **right-now + `/fabrik-review-scoped`** (exists today), and `start` refuses the lane for it.
5. house heuristic, stated as one: more than 3 files? → **spec chain** (`Profile: small` then lightens execution). Grounding: 69% of the last 300 hub commits touch ≤3 non-ledger files; Google treats file count as a size multiplier and names no number; RFC 2904 says size is not the test. It is here because it is the one test the router and the operator can see before any work, never because the literature ranks it.
6. one reversible decision, statable in the six fields, ≤3 files, no sync path, no heavy surface, no mechanism, no trade-off? → **`/fabrik-task`**

**Tripwire (the fallback):** if the first draft cites a script's internals, re-apply the six tests (1, 1b, 2, 3, 4, 5; row 6 is the verdict) by hand (a second `start` only warns `NESTED START` today, `command_run.py:2690-2697`, and after this build would refuse once phase 3 has dirtied the declared paths) — a test that now trips is an UPGRADE, or the draft over-scoped, and the re-application says which. Phase 0's dirty-at-start check catches work done on disk before `start`; this catches the elaboration that happened only in context.

## Lifecycle

- **Adoption / first run:** the build ends with the DOGFOOD — the first `/fabrik-task` is run on a real candidate from the backtest, and the command is not declared done until that run closes.
- **Growth triggers, read from V4's series (each a trigger to re-examine; pass/fail only from n = 78):** a rising `oversized_mini` share → the file or mechanism test is re-examined by a `/fabrik-command-improve` run on this command's queue; a rising `upgrade` share → the rule is too permissive at the top and the table tightens; a median wall-clock drifting toward the chain's → phase 2 or 4 is the suspect; a FALLING adoption share beside a green `oversized_mini` → the lane is being skipped, not gamed (C3's third cobra).
- **The ratchet must not accrete process (DORA's vicious cycle):** an UPGRADE is a hand-off to the lane that already exists, never a new step added to this one; if UPGRADE rates rise, the response is to tighten the six tests at the top, not to add checks inside `/fabrik-task`.
- **Degradation:** if `command_run.py`'s re-measure cannot run (no git, no `declared.sha`), the close records `oversized_mini: unmeasurable` with the reason (`no-git` / `no-sha`) — one sentinel for every instrument gap, counted as a gap and never bucketed as clean (the kaizen collector's own rule).
- **Retirement:** remove the source and, in both CLAUDE.md copies, only the step-0 table's `/fabrik-task` destination (rows 1–5 and the pointers to the table stay — the table without its sixth destination is still the lane rule, and § 1a's sync trigger is correct without the lane), the two doc rows and the tests; in `command_run.py` the phase-0 tests and the re-measure go, while `--declare` and the two row fields stay accepted because closed records reference them; `command_feedback_report.py`'s header stops counting the series the same day, so a retired lane emits nothing; `fabrik-lib` is told by mail.

## External dependencies

**1a — none.** This design is purely internal: no vendor, API, SDK, library, protocol or pricing is touched. Every fact above is grounded in this repo at `path:line` or measured from its ledgers this session.

**1c — approach grounding (live research, this session).** The design's core is a tiered change process with a reversibility-first sizing test and a one-way upgrade ratchet. Grounded live by a `fabrik-researcher` seat, 2026-09-17, each source fetched raw unless marked:

- **A published three-lane system for the identical gap — SUPPORTS the lane.** Rust's compiler team runs PR (light) / MCP (medium) / RFC (heavy): *"RFCs are… a heavy-weight proposal mechanism, reserved for significant changes… MCPs are… a medium-weight proposal mechanism, suitable for most proposals… PRs are… a light-weight proposal mechanism."* — https://forge.rust-lang.org/compiler/proposals-and-stabilization.html. Its founding RFC states the gap in our words: *"a channel for signaling intentions that lies somewhere between opening a PR… and creating a… design meeting proposal or RFC"*, to *"avoid the phenomenon of PRs living in limbo because it's not clear what level of approval is required."* — https://rust-lang.github.io/rfcs/2904-compiler-major-change-process.html. (The forge page says PRs are *also* "suitable for most proposals"; the phrase does not distinguish the MCP tier.)
- **The size test is NOT lines or files — CONTRADICTS a file count as the primary test.** RFC 2904: *"whether something is a major change proposal is not necessarily related to the number of lines of code that are affected. Renaming a method can affect a large number of lines… but it may not be a major change."* Google's design-doc guidance centres the decision on ambiguity and trade-offs: *"At the center of that decision lies whether the solution to the design problem is ambiguous"* and *"If a doc basically says 'This is how we are going to implement it' without going into trade-offs… it would probably have been a better idea to write the actual program right away."* — https://www.industrialempathy.com/posts/design-docs-at-google/. The tests the field publishes are cross-team reach, public contract, new architectural component, reversibility, and ambiguity (designdoc.tech, 2026-04-03, a vendor blog: *"1. Does this affect more than one team?… 2. Is this hard to reverse?… 3. Does this introduce a new architectural component?… 5. Does this change a public contract?"* — its item 4, elided here, is a documentation-value test, *"Will people need to understand this decision six months from now?"*, so the list is not purely blast-radius — https://designdoc.tech/blog/when-not-to-write-an-rfc). **Consequence for this spec:** the decision rule leads with those; the file count is a house heuristic, stated as one.
- **Reversibility is a member of every published test set, never ranked first — SUPPORTS it as mandatory, CONTRADICTS "reversibility first".** The concept itself is not grounded externally: `docs/reference/operating-manifesto.md:10-14` (Phase 0 triage) is this repo's authority on reversible-vs-one-way and the SIZE gate cites it directly. What the field adds is only the ranking: designdoc.tech lists cross-team first and reversibility second; RFC 2904 uses reversibility as one of two shortcut conditions inside the process (*"The FCP can be skipped if the change is easily reversed and/or further objections are considered unlikely"*), not as the classifier.
- **The ≤12-line design is Google's own mini doc — SUPPORTS phase 2.** *"it is absolutely possible to write a 1-3 page 'mini design doc'… you still do all the same steps as for a longer doc, just keep things more terse."* — industrialempathy.com, above.
- **Size guidance that exists names lines and treats files as a multiplier, with no file number — SILENT on "3".** Google eng-practices, which disclaims any threshold first (*"There are no hard and fast rules about how large is 'too large'"*): *"100 lines is usually a reasonable size for a CL, and 1000 lines is usually too large… it's up to the judgment of your reviewer… A 200-line change in one file might be okay, but spread across 50 files it would usually be too large."* — https://google.github.io/eng-practices/review/developer/small-cls.html. SmartBear's own study of a Cisco team (a vendor study) on review effectiveness: *"beyond 400 LOC, the ability to find defects diminishes."* — https://smartbear.com/learn/code-review/best-practices-for-peer-code-review/. DORA: *"working in small batches predicts software delivery performance"* with a TIME threshold (*"longer than a week… is too big"*) — https://dora.dev/capabilities/working-in-small-batches/.
- **The measured gaming shape is salami-slicing, and the counters are published — SUPPORTS the cobra section as amended.** *"There is an incentive to make RFCs as small as possible since the smaller the RFC is, the easier it is to get accepted […] unfinished features where the initial work is done but follow-up work is not tracked."* (the elision spans the author's own concession that this "could be good") — https://www.ncameron.org/blog/the-problem-with-rfcs/. Counters: reviewer-side upward bounce — *"If the approval required… requires an MCP or an RFC, then the contribution should be closed or marked as blocked, with a request to create an MCP or RFC first"*; and *"An earlier accepted MCP is not a substitute for any later necessary approvals."* — forge.rust-lang.org, above. DORA names the mirror cost of the lighter lane being skipped rather than gamed: *"Treating all changes equally… change review is inefficient, and people are unable to devote time and attention to those that require true concentration."* — dora.dev, below.
- **Uniform heavy process is the named pitfall; tiering is the recommendation; but an escalation path must not accrete process — SUPPORTS the lane, WARNS the ratchet.** DORA: *"Treating all changes equally. When all changes are subject to the same approval process, change review is inefficient"* and *"Responding to problems by adding more process […] drives up lead times and batch sizes, creating a vicious cycle."* — https://dora.dev/capabilities/streamlining-change-approval/. designdoc.tech on the mirror risk: *"Once engineers view the RFC process as red tape, they stop engaging meaningfully with the RFCs that actually matter."*
- **The one-way ratchet has direct precedent — SUPPORTS.** The brainstorming skill this design was born in: *"The ratchet is one-way: hidden complexity discovered mid-task upgrades the path — stop, say so, and step up. Nothing downgrades mid-task."* — https://raw.githubusercontent.com/obra/superpowers/refs/heads/main/skills/brainstorming/SKILL.md; RFC 2904: *"if the change proves more controversial or complex, we may escalate towards design meetings, longer write-ups, or full RFCs before reaching a final decision."* A DOWNGRADE path was found in none of the 4 process documents fetched — *not found in 4*, not "does not exist".
- **An alternative shape the field uses — RECORDED as R8.** Oxide scales depth inside ONE artifact rather than adding lanes: *"use your best judgement when it comes to the level of depth to devote to an RFD."* — https://rfd.shared.oxide.computer/rfd/0001.
- **Verified in full text — SUPPORTS "small = few files" as a distribution, names no threshold.** Sadowski et al. 2018, *Modern Code Review: A Case Study at Google*, § "Review size": *"over 35% of the changes under consideration modify only a single file and about 90% modify fewer than 10 files."* — https://doi.org/10.1145/3183519.3183525, read through the DOI's full-text mirror (dl.acm.org answers 403 to fetchers; the abstract does not carry the figures).
