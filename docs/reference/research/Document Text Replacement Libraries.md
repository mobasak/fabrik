# **Architecting Structure-Preserving Text Replacement: A Comprehensive Evaluation of Document Reconstruction Engines**

## **Introduction**

The automated manipulation of document text—specifically the process of extracting semantic segments, applying an external transformation such as translation or redaction, and re-injecting the text while preserving the original layout, typography, and structural integrity—represents a highly complex challenge in document engineering. Unlike pure semantic extraction pipelines that discard visual coordinates, or naive overlay techniques that rasterize pages and destroy selectable text layers, a structure-preserving pipeline must operate bidirectionally. It must seamlessly decouple the visual and spatial metadata from the semantic content during extraction, and subsequently re-anchor the transformed semantics back into the rigid geometric or flow-based constraints of the original document format.
This comprehensive report exhaustively evaluates the libraries, rendering algorithms, and architectural patterns required to build a self-hostable, Python-centric text extraction and reassembly engine. The analysis focuses explicitly on the reconstruction and rendering layer across Portable Document Formats, encompassing both native digital text and scanned rasterizations, alongside Microsoft Office Open XML formats and their legacy equivalents. The evaluation systematically addresses the core failure modes of document reconstruction. These failure modes include embedded font subsetting constraints in PDFs, fixed-layout text-expansion overflow, the complex split-run XML schema inherent to Office formats, and the background degradation issues associated with scanned image text replacement.

## **The Pluggable Architecture and the Intermediate Representation Anchor Model**

To achieve true pluggability—defined as the ability to cleanly separate the extraction of document segments from the application of externally edited segments—the system architecture must completely abandon the concept of end-to-end black-box translation. Operating directly on the document stream for both extraction and replacement inextricably links the semantic logic to the presentation logic, severely limiting the ability to inject pre-translated or externally manipulated text. The optimal architectural solution relies on an Intermediate Representation paradigm, successfully pioneered by open-source translation engines such as BabelDOC and its associated ecosystem.
Treating document translation as an end-to-end task often results in the loss of structural fidelity, semantic truncation, and layout corruption. A bidirectional Intermediate Representation acts as a structured data interface that encapsulates per-page elements into a standardized schema1. By standardizing the input document, the text segments are mapped to stable segment identifiers that are explicitly linked to spatial coordinates, bounding boxes, and stylistic attributes. This unified data structure forms the foundation of the anchor model1.
When an external process, such as a custom translation engine, interacts with the document, it operates solely on the semantic layer of the Intermediate Representation. The translated output is then re-anchored to the original structural constraints via the retained metadata2. This explicit decoupling allows for advanced document-level natural language processing interventions to occur in the middle of the pipeline. Operations such as automatic terminology extraction, cross-page context stitching for paragraphs spanning multiple columns, and the deployment of mathematical placeholders become possible because the layout constraints are temporarily suspended1. Mathematical formulas and non-translatable text fragments can be identified via font-size variance or character patterns, masked as placeholders during the external semantic edit, and subsequently reconstructed with high fidelity during the final rendering phase1.

| Intermediate Representation Component | Architectural Function | Pluggability Advantage |
| :---- | :---- | :---- |
| **Spatial Coordinate Mapping** | Captures absolute bounding boxes for text blocks, lines, and inline images1. | Allows external engines to calculate necessary text-expansion constraints prior to rendering. |
| **Stable Segment Identifiers** | Assigns unique hashes or sequential IDs to discrete semantic paragraphs1. | Enables asynchronous external processing; translated chunks can be rejoined out of order. |
| **Stylistic Attribute Retention** | Records font family, color, size, and weight independently of the text string2. | Prevents the external translation engine from needing to handle markup tags or layout logic. |
| **Formula & Artifact Placeholding** | Detects non-linguistic structures (equations, symbols) and swaps them for tokenized anchors1. | Protects complex mathematical typesetting from being corrupted by large language models. |

The Intermediate Representation model ensures that the extraction phase and the reassembly phase are entirely agnostic to the method of text manipulation used in between. Whether the text is translated via a local neural network, routed through a cloud-based API, or manually edited by a human operator, the rendering engine simply receives the populated Intermediate Representation and executes the reconstruction algorithms.

## **Portable Document Format Reconstruction Layer**

The Portable Document Format standard was fundamentally designed as a digital paper model utilizing an absolute coordinate system for precise visual fidelity4. It is inherently an output format, not an editable canvas. Unlike flow-based formats, PDF text operations do not natively support reflow, dynamic line wrapping, or automatic layout adjustments when content changes.

### **In-Place Text Replacement and the Font Subsetting Constraint**

Achieving true in-place text replacement in a PDF—defined as swapping a text span while maintaining its exact position, matching the original font, size, and color, and producing a real selectable text layer rather than a flattened image overlay—is arguably the most difficult operation in programmatic document manipulation.
A naive approach to this problem involves parsing the PDF and altering the internal content streams directly. However, PDF files practically universally utilize subsetted fonts. When a PDF is initially generated by a word processor or typesetting system, the software embeds only the specific glyphs, or characters, that are actually used in the document to drastically reduce the final file size5. For example, if the original document contains the word "fine" and an external translation engine replaces it with the word "not", the characters 'n' and 't' may be present in the embedded font dictionary, but the 'o' glyph will be entirely missing5. Attempting to force the missing glyph into the existing content stream using the subsetted font will result in a blank space, a missing glyph symbol, or a complete failure of the PDF rendering engine5. Furthermore, sequence combinations such as ligatures further obscure character mapping, as a sequence like "fi" might be encoded as a single composite glyph rather than two distinct characters5.
To bypass the font subsetting limitation without destroying the underlying selectable text layer, the industry-standard workaround relies on the redaction and overlay methodology. Utilizing highly performant libraries like PyMuPDF, which provides Python bindings for the MuPDF C library, the pipeline executes a sequence of destructive and constructive operations.
The extraction phase utilizes dictionary-based text extraction methods to pull text blocks, lines, and individual spans alongside their precise bounding boxes, font sizes, colors, and writing directions7. Once the text is edited externally, the redaction phase begins. The engine applies a redaction annotation over the original text's bounding box and applies the redaction, which permanently strips the original text from the underlying content stream and visually clears the area without rasterizing the surrounding page elements9. Finally, the injection phase inserts the new text at the original spatial coordinates. Because the original subsetted font is unusable for new characters, a visually similar system font or a bundled multilingual font must be explicitly supplied and embedded into the newly generated PDF structure9. This ensures the output remains a true vector document with selectable text, indistinguishable in utility from the original.
Commercial software development kits and APIs provide higher-level abstractions for these tasks, but within the open-source ecosystem, PyMuPDF remains the most capable foundational library for executing precise redaction and text insertion coordinates8. Other libraries, such as pikepdf, excel at structural repair, merging, and raw object replacement, but they operate too closely to the raw stream data to easily calculate text matrices or execute reflow logic for linguistic replacement14. Similarly, libraries like pypdf lack the robust low-level content stream manipulation capabilities required to reliably rewrite text without corrupting the document's cross-reference tables6.

## **Fixed-Layout Text-Expansion and Reflow Algorithms**

When a text segment is replaced via external translation or editing, the new character string is frequently longer or shorter than the source material. Because PDFs completely lack a Document Object Model to automatically push subsequent elements down the page, text expansion results in severe visual overflow. The newly injected text will overlap adjacent columns, run off the edges of the page, or collide with graphical elements, completely destroying the document's layout4.
To handle fixed-layout text-expansion successfully, the rendering engine must implement sophisticated, dynamic auto-fit font scaling, line re-wrapping, and bounding box re-layout algorithms that operate within the strict geometric confines of the original text block.

### **The Knuth-Plass Line-Breaking Algorithm**

For robust typographical rendering within a defined bounding box, standard greedy line-wrapping algorithms—which simply break lines at the first available space character when the boundary is reached—are insufficient. They produce highly uneven ragged edges and awkward spacing. Instead, the implementation of the Knuth-Plass line-breaking algorithm, originally developed by Donald Knuth and Michael Plass for the TeX typesetting system, provides optimal text wrapping and distribution18.
The Knuth-Plass algorithm utilizes a dynamic programming approach to minimize the overall "badness" of an entire paragraph rather than optimizing line by line. The algorithm models text using three primary components. Boxes represent objects of static width, encompassing individual characters, glyphs, or even inline images18. Glue represents the flexible spaces between words. Glue possesses defining mathematical parameters for stretchability and shrinkability, allowing the algorithm to dynamically calculate a ratio to fill a desired line width uniformly18. Finally, penalties represent typographic demerits assigned to undesirable visual outcomes, such as hyphenating consecutive lines, creating orphaned words at the end of a paragraph, or forcing extreme stretching of the glue18.
By calculating potential breakpoints across the entire text block, the algorithm traverses a theoretical network of line breaks to find the path that minimizes the global sum of demerits. This ensures that the newly translated text maintains optimal tightness and consistent density without overflowing the visual container18. Reference implementations of this algorithm exist in the Python ecosystem, such as the pyparagraph and justified libraries, which can be deeply integrated into the PDF rendering layer to calculate optimal string distributions before the text is actually painted onto the PDF canvas20.

### **Adaptive Typesetting and Fallback Heuristics**

State-of-the-art open-source engines dedicated to layout-preserving translation, notably BabelDOC, utilize a progressive, multi-tiered algorithmic approach to handle severe text expansion when forcing translated text into fixed bounding boxes22. The engine mathematically evaluates the target bounding box against the rendered dimensions of the new string and applies a sequence of fallback mechanisms.

| Typesetting Fallback Stage | Algorithmic Mechanism | Trigger Condition |
| :---- | :---- | :---- |
| **Algorithm 1: Sequential Wrap** | Converts all elements into dimensional typesetting units. Places elements sequentially from the top-left of the original bounding box, wrapping to the next line upon reaching the width limit22. | Executed initially. Succeeds primarily when the replacement text is shorter than or equal in length to the original text. |
| **Algorithm 2: Dynamic Scaling** | Initializes a scaling factor of 1.0 and line spacing of 1.5. Progressively reduces line spacing in 0.1 increments down to 1.4. If overflow persists, reduces element scaling (by 0.05 if scale \> 0.6; by 0.1 if scale \<= 0.6)22. | Triggered when Algorithm 1 fails to fit the text within the vertical constraints of the original bounding box. |
| **Algorithm 3: Bounding Box Expansion** | Calculates available right-side whitespace, utilizing up to 90% of the page crop box width. Checks for collision logic against overlapping paragraphs or graphic figures on the right. Expands the box horizontally if space permits22. | Triggered for extreme overflow cases before heavily penalizing the font scale, preventing text from becoming unreadably small. |

Additional layout-preserving typography features are frequently required during this phase to maintain professional aesthetics. For instance, handling mixed script typography requires programmatic interventions, such as automatically injecting a 0.5 character width spacing between Latin characters and East Asian characters to adhere strictly to Unicode Technical Report number 59 guidelines regarding East Asian Spacing22. Furthermore, hanging punctuation rules must be applied to allow specific punctuation marks to extend slightly beyond the right margin, maintaining better visual alignment for the text block as a whole22.

## **Scanned Document Reconstruction and Multimodal Inpainting**

Scanned documents, including JPEGs, PNGs, and rasterized PDF files, pose an entirely different set of challenges because they fundamentally lack selectable text layers. A standard pipeline involves passing the image through an Optical Character Recognition engine, such as Tesseract or PaddleOCR, to extract the text strings and their absolute bounding boxes8. However, simply generating translated text and placing it over the original image using a white-box overlay technique destroys the underlying background. Complex document textures, security watermarks, gradient colors, and adjacent graphical artifacts are obliterated, leading to severe visual degradation and a highly unprofessional output.
A production-grade pipeline for the structure-preserving translation of scanned documents requires a sophisticated multimodal approach involving hierarchical segmentation followed by neural image inpainting24.

### **Hierarchical Text Segmentation**

Optical Character Recognition engines frequently return highly fragmented bounding boxes. The output often consists of disjointed character-level or scattered word-level boxes that completely break semantic continuity, making cohesive translation impossible. To resolve this, advanced computer vision models, such as the Hierarchical Segment Anything Model, are deployed to unify these fragmented boxes into logical typographical structures26.
These segmentation models process the visual features of the document and group the raw Optical Character Recognition boxes into stroke-level, word-level, line-level, and paragraph-level segments26. This hierarchical grouping produces coherent, sentence-like units that are highly suitable for contextual translation25. Crucially, this layout analysis also preserves overarching structural cues, ensuring that bulleted lists, indented paragraphs, or complex diagram labels are mathematically grouped to maintain consistent formatting during the later re-rendering phase25.

### **Background Inpainting and Text Re-rendering**

Before the newly translated text can be rendered onto the document, the original source text must be seamlessly erased from the underlying image tensor. The precise bounding boxes and pixel-level stroke masks provided by the hierarchical segmentation model are converted into binary masks25. These binary masks, along with the original document image, are fed into a lightweight, high-resolution generative inpainting model, such as the Resolution-robust Large Mask Inpainting model25.
The inpainting model analyzes the surrounding context of the document and reconstructs the background texture beneath the text mask. Different architectural approaches exist within the inpainting domain to handle complex document backgrounds. While standard Fourier-based architectures process global image features efficiently, they occasionally struggle with fine-grained structural textures. Alternatively, Wavelet transform-based inpainting architectures offer improved performance for restoring sharp edges and high-frequency details in missing areas, ensuring that lines, borders, and watermarks interrupted by the text are perfectly reconnected29. This process effectively cleans the document, generating a pristine, text-free background canvas25.
Finally, the translated text is rendered back onto the inpainted image. The rendering layer utilizes the spatial coordinates obtained during the segmentation phase and applies the exact same auto-fit scaling and line-breaking algorithms discussed previously, ensuring the new text mimics the original typography and integrates seamlessly into the reconstructed document25.

## **Flow-Layout Formats: Microsoft Office Open XML and Legacy Structures**

Microsoft Office Open XML formats, specifically DOCX and XLSX, are structurally divergent from PDFs. They utilize a flow-based Document Object Model encapsulated within compressed XML archives. While text-expansion naturally reflows in these environments—eliminating the need for complex Knuth-Plass line breaking—the primary challenge lies in preserving highly localized character styling and navigating complex, nested XML objects during programmatic text replacement.

### **Resolving the Split-Run XML Problem in DOCX**

In the DOCX standard architecture, textual content is deeply nested. A paragraph element contains multiple run elements, which in turn contain the actual text node elements30. A run represents a sequential string of characters that share entirely identical formatting properties, such as font family, font size, bolding, italics, and color30.
A critical failure mode occurs when developers attempt to replace text using standard libraries without understanding this underlying schema. If a script searches for a paragraph containing a specific string and assigns new text directly to the paragraph object, the library will replace all existing XML content within that paragraph boundary with a single, unformatted run. All run-level formatting, including crucial emphasis or colored text, is permanently and irreversibly destroyed33. Furthermore, Microsoft Word processors frequently split continuous words across multiple runs arbitrarily, even when no formatting changes occur. For example, a target translation string might be split across two separate XML runs, rendering a naive search-and-replace function completely useless because the complete string does not exist within any single text node37.
To perform true structure-preserving text replacement in DOCX files, the extraction and rendering pipeline must utilize an index-mapping algorithm, a technique successfully implemented in specialized open-source tools within the ecosystem37.
The algorithm first iterates through a paragraph, treating the combined text of all its runs as a single, unified string. It creates a precise coordinate map for every character, recording its specific XML run identifier and its character index position within that run33. When the external translation engine targets a string for replacement, the algorithm utilizes this map to isolate the exact subset of run and character coordinates that comprise the source string across the XML boundary.
To execute the replacement without corrupting the schema, the engine injects the entirety of the new, translated text into the very first run of the matched sequence, forcing the new text to adopt the exact formatting properties of the beginning of the original string. The text content corresponding to the match in all subsequent runs is then systematically deleted by emptying the nodes, preserving the visual flow and the integrity of the surrounding XML schema37.
Beyond the main document body, the extraction and injection pipeline must be engineered to recursively traverse parallel XML components. Text is frequently hidden within tables, nested tables, section headers, section footers, and footnotes. These elements are stored in distinct objects and require separate iteration logic33. Specifically, traversing headers requires evaluating the inheritance properties of sections to ensure linked headers are not inadvertently overwritten or duplicated41. Merged table cells require highly specialized parsing, as attempting to iterate through a non-uniform grid logic will trigger list index out of range exceptions, causing the entire pipeline to crash43.

### **Cell-Level Precision and Rich Text in XLSX**

Excel format manipulation via Python libraries poses distinct and highly specific challenges regarding cell value replacement, the preservation of underlying mathematical formulas, and the handling of rich text strings within individual cells.
The foremost consideration is formula preservation. When loading the workbook into the processing pipeline, the software must be explicitly instructed to retain formulas. If the data-only flag is inadvertently activated during the initial parsing phase, all formulas within the workbook are permanently stripped and irreversibly replaced with their last calculated static values, destroying the document's utility44.
Unlike the DOCX format, styles in Excel, such as background fills, borders, and overarching cell fonts, are bound directly to the cell object itself, rather than the string value contained within it. Replacing the value of a cell with translated text safely retains the original overarching cell formatting, provided the cell previously contained data to anchor the style46.
However, a significant architectural complication arises when a single cell contains rich text—multiple text formats applied to different words within the same cell, such as a single bolded word within a standard sentence. The parsing library models this utilizing a specialized rich text object, which consists of a list of text block elements. Each block contains an inline font definition and an isolated text segment48. If an external translation process replaces the entire cell value with a standard Unicode string, all rich text metadata is instantly destroyed. The extraction engine must be programmed to parse these rich text blocks individually, generating distinctly tagged sub-segments for the translation engine. Upon receiving the translated output, the rendering layer must reassemble these segments into a properly formatted rich text object before injecting it back into the worksheet cell49.
Finally, hyperlink preservation requires targeted logic. Hyperlinks in Excel are managed as separate relational objects, distinct from the visible cell values. An extraction engine must independently iterate over the hyperlink objects within a worksheet to translate the visible link text without corrupting the underlying uniform resource locator address51.

### **Legacy Binary Formats**

Legacy binary formats, specifically the older DOC and XLS file types, are fundamentally incompatible with modern XML-based parsing libraries. Because these formats rely on proprietary object linking and embedding binary structures, they lack reliable, open-source Python manipulation libraries capable of executing complex structural edits or granular text replacement.
To process these files within a structure-preserving pipeline, they must be converted to their modern Office Open XML counterparts prior to extraction. This conversion is typically achieved programmatically by spinning up a headless LibreOffice instance to handle the translation of the binary stream into XML, or by utilizing a component object model wrapper on Windows-based server environments to leverage the native Microsoft application layer. Following the editing and reassembly phase, the files can optionally be converted back to their legacy extensions, although the probability of experiencing fidelity loss or formatting degradation during this binary conversion round-trip is exceedingly high.

### **System Breakdown Points**

While these libraries provide powerful capabilities, specific operational limitations dictate where each option fundamentally breaks down in a production environment.
Deploying PyMuPDF as a standalone solution breaks down rapidly when confronted with fixed-layout text expansion. While extracting and replacing text is relatively trivial, if the newly translated text is longer, it will print over adjacent columns, obscure images, or run off the page entirely unless the developer commits to building a custom Knuth-Plass implementation from scratch. Furthermore, it fails to perfectly match original subsetted fonts, forcing the system to fall back on generic font families, which subtly degrades the document's aesthetic.
Attempting to use legacy tools like pypdf breaks down completely for in-place editing. The library is simply not designed to reliably rewrite raw content streams without corrupting the internal PDF structure and cross-reference tables6.
Utilizing the vanilla python-docx library breaks down entirely on formatting preservation. Executing standard regular expressions or simple string replacements on paragraph objects immediately wipes out all bolding, italics, and custom colors, necessitating the specialized run-mapping algorithms detailed previously33.
Even highly specialized engines like BabelDOC encounter breakdown points when handling complex Right-to-Left languages, such as Arabic or Hebrew. Because its typesetting engine relies on custom-built heuristics that inherently assume Left-to-Right layout calculations, processing Right-to-Left text requires a total refactoring of the engine to integrate the Unicode Bidirectional Algorithm and complex text shaping logic60.

## **Conclusions and Architectural Recommendations**

Constructing a self-hostable, Python-based document engine capable of extracting text, facilitating external edits, and flawlessly reassembling the document requires a highly modular, format-specific architecture. A monolithic approach attempting to force a single library to handle all file types is mathematically and structurally unfeasible.
For processing native PDF documents, the system must adopt the Intermediate Representation architecture demonstrated by advanced frameworks like BabelDOC. The extraction layer should leverage PyMuPDF to extract text spans, embedded fonts, and absolute bounding boxes, funneling this metadata into a structured JSON payload for the external translation engine. Upon receiving the translated output, the rendering layer must execute the redaction and overlay technique. Crucially, the rendering engine must incorporate dynamic scaling algorithms to automatically adjust font sizes, manipulate line spacing, and selectively expand bounding boxes, ensuring the expanded text fits flawlessly without overlapping adjacent visual elements.
For scanned PDFs and rasterized images, the extraction layer must deploy an Optical Character Recognition engine, followed immediately by a hierarchical segmentation model to cluster the scattered character bounding boxes into logical, translatable paragraphs. The rendering layer must utilize a neural inpainting model to erase the original text regions while perfectly preserving the complex background textures. The new text is then painted onto these cleared bounding boxes using the same text-expansion heuristics applied to native PDFs.
For flow-layout formats like Microsoft Word, the engine must abandon naive paragraph replacement and implement robust index-mapping techniques. By calculating character offsets across multiple XML runs, the engine can safely replace text while inheriting the styling of the matched run and clearing subsequent runs, effectively defeating the split-run problem. This extraction logic must be applied recursively to guarantee that headers, footers, footnotes, and deeply nested tables are fully processed.
Finally, for Microsoft Excel formats, the pipeline must explicitly parse and reconstruct rich text block objects to preserve granular, partial-cell formatting. The workbook must be initialized strictly without data-only flags to prevent the catastrophic destruction of embedded spreadsheet formulas during the manipulation and save operations.
By implementing this format-specific, metadata-anchored architecture, the pipeline achieves the complete separation of semantic extraction from visual rendering, ensuring maximum layout and typographic fidelity across the entire spectrum of targeted document formats.
