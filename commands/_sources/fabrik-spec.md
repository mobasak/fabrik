## Phase 1 — DUAL GROUNDING (gated — do NOT propose approaches before BOTH are satisfied)

Two axes: live external truth AND what Fabrik already has.

### 1a — External facts: BLOCKING live-research gate

For **every** external dependency the idea touches — 3rd-party API / SDK, vendor, **pricing, rate limits**, library, framework, protocol, standard — ground it to **CURRENT truth**, never from training memory.

- Order: **repo-first** (`grep docs/`, `docs/reference/`, `AFCL.md`) → then **live research**: `WebSearch` / `WebFetch` → `mcp__brave-search__brave_web_search` → on a miss `mcp__exa__web_search_exa` / `mcp__firecrawl__firecrawl_search` / `firecrawl_scrape` (scrape with `proxy: "basic"`) on the library's OFFICIAL docs site for framework/API detail (`WebFetch` only to locate the page) → the **`gh` CLI** (`gh search code` / `gh api -H 'Accept: application/vnd.github.raw' repos/<o>/<r>/contents/<path>` / `gh release list`) to read a dependency's ACTUAL source, confirm a signature, or check its latest release/open issues when docs are thin or a claim needs verifying against the real repo (authenticated, zero idle processes — D-014 retired the github MCP).
- Capture the **real** endpoint / signature / auth model / limits / pricing from a RAW fetch (`firecrawl_scrape` as markdown with `maxAge: 0` and `proxy: "basic"`, the raw `gh api` call above, the raw file — a `WebFetch` reply summarises, below) and **cite the source URL + the date you fetched it** in the spec — the machine-readable schema when one exists (an OpenAPI endpoint names the parameters), the error-code page beside the endpoint page when the design retries or re-sends, and a design that survives both readings when two vendor pages contradict each other. A build-tool setting the design relies on (any bundler, compiler, test-runner, package-manager or CI option, a config file's default included) is settled by a build you run or by the tool's own source read through `gh` — its docs page locates the setting but never settles it — else it is a named BLOCKING unknown.
- **Local claims are executed, not cited:** every premise the brief states about the codebase, every mechanism the design relies on ("X fires", "Y catches this"), every design rule (an algebra, a classifier) and every runtime-state claim is EXECUTED this session, its command and output cited in the spec (a key, token or credential in that output is described by its kind, length and a non-secret prefix, never pasted, its BEGIN line included: the `detect-private-key` commit hook refuses a private-key PEM header), and Phase 3 waits on it as on the BLOCKING bullet below. A design rule that names stores (a matrix, an allowlist, an entity schema's fields) is preceded by an executed census of each store's current members, its invariants written against that census, never against one member. An executed in-repo measurement outranks a web answer about the repo's own code; a vendored or installed third-party package's behaviour stays an external claim. A design that changes what an existing function, value, build script, table or pattern does, holds, matches or grants is preceded, before Phase 3, by an executed census of its readers, its command and output cited in the spec and each reader named there for the plan's File Scope (`/fabrik-plan-after-chat` Phase 1's reader census, extended here to tables and patterns): a symbol's, value's or script's readers by its call sites (`find_referencing_symbols`, a build script's callers followed transitively) plus a grep of its name, its file's basename and its path; a table's SQL statements, views, ORM models and migrations, found by its bare and schema-qualified names; a matcher's (a gate pattern's) corpus, searched with the flags read from its call under the old pattern and the new. A subject another repo can read (a fleet-synced file, a hub script, API, path or value) is censused across repos: `find` lists the repos, installed dependency directories (`node_modules`, `.venv`) pruned, then each repo found is scanned.
- **Freshness (CLAUDE.md):** the research must be run in THIS session. An external claim with no fresh cited source is a defect.
- **BLOCKING:** you may NOT present approaches (Phase 3) until every external dependency is either grounded-with-a-cited-source, OR recorded as a **named BLOCKING unknown with an explicit resolution step**. Never silently assume a vendor API behaves a certain way.

### 1b-bis — Fabrik hard constraints + architectural mandates (BINDING — they CUT approaches)

**An approach that violates one is not an option: cut it — no matter how well-cited the best-practice research is.** (Grounded in `agents-fabrik.md` § Planning Constraints + § Architectural Mandates.)

**Hard constraints — a cited "best practice" that trips one is DEAD ON ARRIVAL:**

- **LLM gateway = OpenRouter by DEFAULT; vendor SDKs and PAID direct vendor APIs stay banned** (`openai`, `@anthropic-ai/sdk`, `google-cloud-aiplatform`). Direct FREE-TIER OpenAI-compatible HTTP endpoints ARE allowed when dispatched through the `subagents` provider registry (`providers.py`/`nvidia_models.py` — raw httpx to a `/v1`, never an SDK).
- **Vector-DB ban.** pgvector on `postgres-main` only — **Pinecone / Qdrant / Weaviate / Milvus = reject.**
- **Billing routing.** TR domestic → **PayTR** (primary) with **iyzico** as its fallback; international → **Paddle** (MoR); mobile digital goods → **RevenueCat + IAP**. ⚠️ **Stripe is NOT available to the TR entity — never design around it.** ⚠️ **Two different kinds of fact live in this bullet and they age differently.** The Stripe exclusion is STRUCTURAL (Turkey is not a Stripe-supported country) and does not go stale; the named processors are a VENDOR CHOICE and do — PayTR replaced iyzico as the domestic rail on 2026-09-03 (fabrik-lib D-080, operator ruling), while this section still cut any design proposing it. A bullet in this list DISCARDS an approach, so before treating a named processor as fixed, check `docs/DECISIONS.md`; a design contradicting only the vendor half is a decision to surface, not an option to kill.
- **Email two-stream** — transactional and marketing on separate streams/subdomains.
- **Auth = self-host by default** (`fabrik-lib/fastapi-user-auth`, Pattern A). Supabase is retired (ADR-recorded exception only).
- **No Alpine** (Debian `-slim` bases on the registry's `debian_codename`, `.windsurf/rules/versions.yaml`) · **x86_64** (`linux/amd64`) · **no host `ports:`** (Traefik routes) · **storage** = `fabrik-lib/storage` (B2).

**Architectural mandates — every design inherits these:**

- **Concurrency** — every service handles simultaneous requests; never single-threaded blocking.

**12-Factor — ALL TWELVE bind the design** (https://12factor.net/, re-verified 2026-07-12). A design that trips any of these is **not a valid approach — cut it:**

### 1c — Best-practice / approach: BLOCKING live-research gate

Grounding the FACTS (1a) is **not** grounding the APPROACH. Before Phase 3, research the CURRENT best way to build this — never pick an approach from training memory or first instinct:

- Use the wired tools (`WebSearch`/`WebFetch` → `mcp__brave-search__brave_web_search` → on a miss `mcp__exa__web_search_exa` / `mcp__firecrawl__firecrawl_search`) to find, for the **core** of the design, the **current best-practice / pro-grade / LEANEST / lowest-maintenance** way the field actually does this now: the standard library/pattern, the fewest moving parts, the simplest thing that is still production-grade (not a toy, not gold-plated). Bias toward **low/no-maintenance** (managed/boring/proven over shiny; fewer components; within the fabrik self-host default) and **lean** (the smallest design that meets the goal — YAGNI).
- **Cite the source + date** for each best-practice/leanness claim in the spec's Chosen-approach section, and **actually fetch it this session** (`WebFetch` / `firecrawl_scrape` with `proxy: "basic"`). ⚠️ **To QUOTE, fetch the RAW document** (`raw.githubusercontent.com`, view-source, `firecrawl_scrape` with `maxAge: 0` and `proxy: "basic"`, a live fetch) and match the string — normalising whitespace first (raw HTML wraps lines mid-sentence): a `WebFetch` reply is a small model's ANSWER about the page, not an extract, and quoting it ships a sentence the page does not contain. 
- ⚠️ **A cached/mirroring fetch tool is NOT a liveness oracle.** `mcp__exa__web_fetch_exa` serves crawl cache: it returned a complete page for `docs.exa.ai/reference/find-similar-links`, which actually **307s to an HTTP 404**. So an **existence or liveness claim** grounded ONLY through a mirroring fetch returns a **false CONFIRMED**; it needs a **NON-CACHING second path** that reports a STATUS CODE. ⚠️ **The ORCHESTRATOR owns that probe, not the grounder** — `fabrik-researcher` has `Bash` in its `disallowedTools` (`/opt/fabrik/commands/_agents/fabrik-researcher.md`, the frontmatter key — grep it, line anchors drift), deliberately, because it is read-only; instructing it to run `curl -sSI -L -o /dev/null -w '%{http_code}'` is instructing it to fail. Division of labour: the grounder returns CONTENT and its source; **you** run the status probe from the orchestrator shell — or use `WebFetch`, accepting that it answers about a page rather than reporting a code. Every other shell-only check is yours from the shell too, with no `WebFetch` fallback — for example a count over a fetched file, which you download and count yourself, and a seat's quote matched — whitespace normalised first, as the quote rule says — against your own raw fetch when the raw-fetch tools are down. And **absence from a vendor's `llms.txt` is weak sole evidence of removal** — that file is a curated index, not a manifest. "Best practice is X" / "this is the lean option" with **no fresh cited source is a defect**. If the design cites a **standard/RFC** (OAuth, an HTTP spec, a W3C/IETF doc), fetch the primary doc and quote the exact clause — don't paraphrase from memory (that's the hallucinated-citation defect `/fabrik-spec-review` re-checks; catch it here).
- **⚠️ Filter the research through § 1b-bis BEFORE it reaches Phase 3.** The web's "current best practice" will confidently recommend **Stripe**, **Pinecone**, or a direct **OpenAI SDK**, all with excellent citations. **A well-cited best-practice that violates a hard constraint is WORSE than no research.** Cut it, and pick the best option that *survives* the constraints (then cite THAT).

## Phase 2 — Collaborative Q&A (pin intent)

Ask the **minimum** questions to pin the design — **one question at a time**, multiple-choice when possible. **⚠️ Question bar — ask ONLY when a question clears BOTH tests; otherwise decide it yourself and move on:**
1. The answer **materially changes the design or outcome** (not cosmetic, not trivially reversible), AND
2. You **genuinely cannot resolve it** from a convention, `CLAUDE.md`, the codebase, or an obvious default.

If it fails either test, pick the sensible default, apply the convention, and record it in ONE line the user can override later. **Never interrupt for:** folder / file / variable / table / endpoint names, field ordering, log wording, test-file placement, formatting, obvious version pins, or any choice with a Fabrik convention (naming = kebab-case per `CLAUDE.md`; DB host = `postgres-main`). **Do interrupt for:** ambiguous scope, a product/behaviour decision with no default, a data-model or security tradeoff, conflicting requirements, or anything irreversible/destructive. ## Phase 3 — Approaches (2–3) + recommendation

Propose 2–3 approaches with tradeoffs; the judge panel below ranks them, and only then does your write-up **lead with your recommendation and why.** Each MUST be justified against Phase 1: which fabrik-lib modules it **vendors / enhances**, what it **builds** (and why that's unavoidable), which external APIs it uses **with their real grounded limits/pricing**, the `shape:` implications, **and which cited current best-practice (1c) makes it the lean / low-maintenance / pro-grade choice** (a memory-based "best practice" is not valid grounding). Cut any approach that ignores an existing fabrik-lib module, an external API's real constraint, **or the cited best-practice research**.

**Score every approach against the owner's 5 decision criteria:**

1. **Quality first** — production-grade, no shortcuts. Never sacrifice quality to save money.
2. **Total cost of ownership** — **dev time is the most expensive resource.** A $10/mo managed service that saves 2 weeks of dev is a WIN.
3. **Speed to ship** — prefer what deploys through the standard pipeline (`fabrik apply`).
4. **Easy to maintain** — when two options both work, take the one needing less ongoing attention.
5. **Set and forget** — prefer low-maintenance (self-hosted `postgres-main`/`redis-main`; managed Paddle/Cloudflare/Resend where a managed edge genuinely wins) over anything that needs babysitting.

**Then run the 6 reality-challenges — kill any approach that fails one:**

- **Expensive where free exists?** A paid service where a deployed VPS service already solves it (Apprise, Gotenberg, MeiliSearch, Backrest, n8n).
- **Complex where simple exists?** K8s / service-mesh / custom auth proposed → SSH + Docker Compose + Authelia handles it.
- **Build where consume exists?** Check prebuilt containers, the live microservice (site-provisioner), and `/opt/fabrik-lib/` (the 1b ladder).
- **High-maintenance where set-and-forget exists?** Prefer what auto-heals / auto-backs-up / auto-monitors via the existing Prometheus/Gatus/Backrest stack.
- **Incompatible with Fabrik infra?** Port conflicts (`PORTS.md`), Alpine, `localhost` assumptions (use `postgres-main:5432`), non-amd64, 12-Factor violations.
- **Duplicate functionality?** Re-check `docs/BUSINESS_MODEL.md` § Portfolio.
