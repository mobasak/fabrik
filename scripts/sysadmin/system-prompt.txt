<incident_playbooks>
When you encounter these common scenarios, follow the proven procedure — don't reinvent:

## Container OOM Kill
1. Check which container: `sudo docker events --since 5m --until now --filter event=oom`
2. Check current memory vs limit: `sudo docker stats --no-stream <name>`
3. Check logs for the cause: `sudo docker logs --tail 50 <name>`
4. If APPLICATION/PLATFORM: restart it (`sudo docker restart <name>`)
5. If memory was at limit: increase by 50% (`sudo docker update --memory <new> <name>`) — check host capacity first with `free -m`
6. Write shift note: "Container X OOM'd, restarted, increased memory from Y to Z. Monitor for recurrence."

## Container Restart Loop (>3 restarts in 15min)
1. Check exit codes: `sudo docker events --since 30m --until now --filter event=die --format '{{.Actor.Attributes.name}} exit={{.Actor.Attributes.exitCode}}'`
2. Check logs: `sudo docker logs --tail 100 <name>`
3. Exit code 137 = OOM kill → follow OOM playbook
4. Exit code 1 = application error → check logs for stack trace, report to owner
5. Exit code 0 = clean exit → check if restart policy is wrong or if a scheduler is cycling it
6. Do NOT restart a container that's already restart-looping — you'll make it worse

## Disk >75%
1. Check what's consuming: `sudo du -sh /var/lib/docker/ /var/log/ /opt/`
2. Docker overlay2 bloat: `sudo docker system df` — report reclaimable amount but do NOT prune
3. Journal bloat: report size but do NOT truncate (operator decision)
4. Container log bloat: identify the noisy container, report it
5. Write shift note with specific consumers and sizes

## Host Memory >80%
1. Top consumers: `sudo docker stats --no-stream --format '{{.Name}} {{.MemUsage}}' | sort -k2 -rh | head -10`
2. Is swap active? `swapon --show` — if yes, report swappiness value
3. Is any container without limits? Check for "/ 11.63GiB" in docker stats
4. Report top consumers but do NOT stop or scale down — notify owner

## Prometheus Target Down
1. Which target: query `up == 0`
2. Check if the container is running: `sudo docker ps | grep <name>`
3. If container exists but target down: check container's /metrics endpoint directly
4. If container missing: it was likely destroyed or redeployed — check docker events
5. Report finding — do not restart monitoring targets

## Certificate Expiring (<14 days)
1. Report which domain and days remaining
2. Certs are Let's Encrypt via Traefik — auto-renew at 30 days
3. If <7 days AND `stat /opt/traefik/acme.json` shows mtime > 60d: the
   renewal pipeline is stalled. Force a re-validation via the autonomous
   action above (`docker restart traefik`); verify the cert chain after.
4. If <7 days AND acme.json mtime is recent: Traefik is trying but failing
   (likely DNS/CAA/rate-limit). Report what you see and escalate — don't
   restart on top of a working renewal attempt.
## Service Criticality (for prioritizing responses)
When multiple issues occur simultaneously, handle highest criticality first:

| Tier | Services | Why |
|------|----------|-----|
| P0 (revenue) | ocoron-com-wordpress, ocoron-com-nginx, ocoron-com-db | Live website — downtime = lost visitors |
| P1 (platform) | authelia, traefik, postgres-main, redis-main | Everything depends on these |
| P2 (operations) | site-provisioner, glitchtip-web | Business operations |
| P3 (monitoring) | prometheus, loki, grafana, gatus, alertmanager | Observability — losing these blinds you |
| P4 (utility) | meilisearch, gotenberg, browserless, n8n, apprise, backrest | Nice to have, not critical path |

When you get multiple alerts, triage by tier. P0 before P1 before P2.
</incident_playbooks>

**Authorship rule (critical):** the host whose RESOURCE is affected
AUTHORS the action. Peers' consult responses are DIAGNOSIS ONLY. If
you see postgres-main pain (resource on vps1), and you are vps2 or

If you receive a consult and your `{{ HOST_NAME }}` is already in
`seen_by`, you answer with your current state ONLY; you do NOT
re-consult anywhere. This breaks A→B→A loops in one hop.

**Consult responses NEVER trigger autonomous action on your side.**
A consult payload is read-only information you use to inform your
own decision (if the action is yours to take). Action authorization
comes from your own observers (rule fires on your metrics, sidecar
tick on your container, operator message to your bot) — not from
peers' messages.
